name: jira-log
description: Fetch a Jira ticket, create subtask(s) under it, assign to me, set story points, log work, and write a short description of what we did
argument-hint: <TICKET-KEY> [free-form overrides, e.g. "2 subtasks, 1h worklog, 2 points each, fix version v10.3, mark done"]
allowed-tools: mcp__claude_ai_Atlassian__getAccessibleAtlassianResources, mcp__claude_ai_Atlassian__getJiraIssue, mcp__claude_ai_Atlassian__getJiraProjectIssueTypesMetadata, mcp__claude_ai_Atlassian__getJiraIssueTypeMetaWithFields, mcp__claude_ai_Atlassian__createJiraIssue, mcp__claude_ai_Atlassian__editJiraIssue, mcp__claude_ai_Atlassian__addWorklogToJiraIssue, mcp__claude_ai_Atlassian__atlassianUserInfo, mcp__claude_ai_Atlassian__lookupJiraAccountId, mcp__claude_ai_Atlassian__getTransitionsForJiraIssue, mcp__claude_ai_Atlassian__transitionJiraIssue, AskUserQuestion
disable-model-invocation: true

Arguments: $ARGUMENTS (if empty or not substituted, take them from the user's message)

The first token is a Jira issue key (e.g. `PROJ-123`) — this is normally the *parent* under which to create subtask(s), but if the user's wording is about *editing an already-created subtask* ("update IDP-12897 to...", "same for the subtask under IDP-12802", "fix the one you just made"), treat it as the *target* issue to edit directly instead of creating a new one. Don't create a duplicate subtask when the intent is clearly to correct/extend an existing one — check recent conversation context for a subtask key that was already created under the given parent this session.

Everything after the key is free-form text that may override the defaults below or request additional field changes — parse it naturally, do not require exact flag syntax. Examples of valid overrides: "2 subtasks", "worklog 1h", "1h worklog and 2 story points", "3 subtasks of 2 points each", "no worklog", "make it a sub-task not a bug", "affected and fix version v10.3", "mark it done".

Defaults (used unless overridden in the arguments):
- Number of subtasks: 1
- Story points per subtask: 1
- Work log per subtask: a realistic, varied duration sized to the actual work done (e.g. `45m`, `1h 15m`, `2h`, `3h 30m`) — never a fixed `30m` every time, and when creating several subtasks give each its own duration
- Assignee: the current authenticated Jira user, always, unless the user explicitly says otherwise
- Issue type: plain "Sub-task"/"Subtask" (see step 3 — never a specialized variant unless asked)
- Affects Version / Fix Version: the user's value if given; otherwise copied from the parent ticket; if the parent has none, the latest version in the project (see step 7a). If several candidates exist, always pick the latest (highest version number / most recent release date).
- Component(s): the user's value if given; otherwise always ask the user via `AskUserQuestion` which part they worked on, before the confirmation step. Offer the parent's component(s) first (marked "(Recommended)" if any) plus other components from the project's `allowedValues` (via `getJiraIssue` with `expand: "editmeta"`) that fit the work done this session, and allow multi-select. Never silently inherit the parent's component.
- Status: transition the subtask to Done after all fields are filled (Jira won't allow Done until story points, worklog, versions and component are set), unless the user says not to.

Steps:
1. Resolve the Jira `cloudId` via `getAccessibleAtlassianResources`. If there's only one accessible site, use it. If there are several, pick the one whose Jira contains the given ticket key's project (or ask if ambiguous).
2. Fetch the parent issue with `getJiraIssue` (fields: `summary`, `project`, `issuetype`, `versions`, `fixVersions`, `components`) to get its `project.key` and the default versions/components to inherit.
3. Call `getJiraProjectIssueTypesMetadata` for that project and list the issue types where `subtask` is `true`. If there's only one, use it. If there are several (e.g. a plain "Sub-task" alongside specialized ones like "Subtask-Bug" or "Product Enhancement"), default to the plain generic one (named exactly "Sub-task" or "Subtask") — do NOT infer a specialized type from the parent's own issue type (a Defect parent does not imply a "Subtask-Bug" child; that guess has been wrong before). Only use a specialized subtask type if the user's arguments explicitly ask for it. Use the exact `name` and `id` from this response either way — never hardcode either string.
4. Call `getJiraIssueTypeMetaWithFields` (that project + the subtask issue type id, `requiredFieldsOnly: false`) and find the field whose name matches "Story Points" or "Story point estimate" (case-insensitive) — remember its `customfield_...` id. This id varies per Jira project/site, so always look it up fresh; never hardcode one. If no such field exists on this project, skip setting story points later and say so plainly in the final summary instead of failing the whole skill.
5. Call `atlassianUserInfo` to get the current user's `accountId`. If it doesn't return one directly, fall back to `lookupJiraAccountId` with the user's email.
6. Write a short description of the actual work completed in this conversation — 2 to 4 concise sentences or bullets, no filler. Pull this from what was actually done earlier in this session, not from the ticket's existing content. If creating more than one subtask, split the work into that many logically distinct pieces; otherwise write one combined summary for the single subtask.
6a. **Confirm before writing anything.** Resolve all values first (versions per step 7a, components, story points, worklog per subtask, summary, description, target status), then show the user one compact table of everything that will be set and ask via `AskUserQuestion` whether it's correct (options: "Looks good, proceed" / "Change something"). If they want changes, apply them and ask again. Do not call `createJiraIssue`, `editJiraIssue`, `addWorklogToJiraIssue` or `transitionJiraIssue` until confirmed.
7. For each subtask to create (skip this step entirely if the arguments target an existing subtask for editing instead — go straight to step 7a/7b/7c on that issue):
   - Call `createJiraIssue` with the resolved `cloudId`, `projectKey`, `issueTypeName` (from step 3), `parent` = the parent issue key, a short `summary` derived from the work (imperative mood, under ~80 characters), `description` (from step 6), `assignee_account_id` (from step 5), `components: [{ id }]` in `additional_fields` (from step 2 / user), and — only if a story points field was found in step 4 — `additional_fields: { "<fieldId>": <storyPoints value> }`.
   - Call `addWorklogToJiraIssue` on the newly created subtask's key with `timeSpent` set to the resolved worklog duration (varied, per the defaults).
   - If the arguments also ask to change the issue type (e.g. "make it a sub-task not a bug"), call `editJiraIssue` with `fields: { issuetype: { id: "<id from step 3>" } }` — this works for switching between subtask-level types in the same project.
7a. Always set Affects Version and Fix Version (resolve these before step 6a). If the user supplied one, do NOT use the literal string they typed — call `getJiraIssue` on the target issue with `expand: "editmeta"` and `fields: ["versions", "fixVersions"]`, read the `allowedValues` list from the returned `editmeta`, and match the user's version number against it as a substring (project version names are often prefixed, e.g. the user's "v10.3" may actually be named "IDP v10.3" in the project — a bare-string edit will be rejected with "Version name '...' is not valid"). Then call `editJiraIssue` with `fields: { versions: [{ id: "<matched id>" }], fixVersions: [{ id: "<matched id>" }] }`. If the user supplied nothing for a field, use the parent's value for it (from step 2); if the parent has none, pick the latest version from `allowedValues` (highest version number, preferring unreleased/most recent release date). If multiple values are candidates, always use the latest.
7b. After versions, component, story points and worklog are all set, move the subtask to Done (or the status the user asked for; skip if they said not to): call `getTransitionsForJiraIssue` on the target issue, match the desired status against the `name`/`to.name` of the returned transitions, then call `transitionJiraIssue` with that transition's `id`. Never guess a transition id. If the transition fails for a missing required field, report which field and fix it rather than giving up.
7c. If the arguments mention a story points or worklog change for an *existing* subtask, use `editJiraIssue`/`addWorklogToJiraIssue` directly on that issue rather than creating anything new.
8. Report back concisely: each affected subtask's key and a link, and every field that was set (story points, worklog, affects/fix version, component, status, issue type) or explicitly skipped (e.g. "no Story Points field on this project", "no version matching '10.3' found — closest options were: ..."). Never silently drop a requested change.

Never modify or transition the parent issue itself — everything above applies only to the subtask(s), whether newly created or referenced for editing.
